Muldro · view layer

Frame and body

Every card muldro shows you today is assembled from nineteen optional slots by whichever producer happened to run. This is the replacement: code owns the frame, the model writes one markdown body, and text from outside the system never enters either.

What follows is the shape, how it is generated, how it scales across five connectors, and how it renders at both depths — on the autonomous loop and in chat. Specimens use muldro's real palette and type, so they show the actual product, not a mockup of one. All seven design forks are settled.

The only encoding you need

Three authors, three colours

These three hues carry the entire argument. They mean the same thing in every diagram, specimen, and snippet on this page.

Code · frame Identity, kind, status, source, timestamp, importance, buttons. Built from a database row. Deterministic. Never model-authored.
Model · body One markdown field. muldro's own prose, in muldro's own voice — what it thinks and why. The only thing the model writes.
External · quoted An email subject, a message body, a fetched page. Reaches the screen only as a quote with a name attached. Never a headline, never inside the body.

Why each defect is now unrepresentable

1 One body string, one renderer. There is no second projection to disagree with. Defects 1 and 2 have nowhere to live.
2 The headline is frame, built from the thread row. It is the counterparty and the subject muldro resolved — not a string the pipeline salvaged. No fallback constant, because there is nothing to fall back from.
3 Buttons are frame. Affordances come from the capabilities the thread actually admits, with labels written in code. The model can argue for one in the body; it cannot mint one.
4 Evidence is the quote. Real external text, verbatim, attributed to a named human. Not a number the model chose.
5 The link-injection hole closes as a side effect. Headlines are plain text. External strings reach the screen only through the amber band, which code renders and attributes.

The coloured rails are annotation for this page — in the product the bands read as ordinary typography. What survives visually is that every card of a kind is the same shape, because the shape no longer depends on which optional fields happened to be non-null.

How it is generated

Where the email is allowed to go

This is the load-bearing mechanism. The rule is not "don't quote email text in your summary" — that is a prompt instruction, and it is unenforceable because the model has the text in context and no way to prove it didn't use it. The rule is structural: the body slot never carries external provenance, because external values arrive on a different field that only code renders.

What the producer actually writes

The model's entire contract becomes one field. Not nineteen slots, not a component tree, not a kind it chooses for itself.

the object a producer emits
// built by code from the thread row — the model never sees these as writable
frame: {
  key:        "thread:gh_01J…"   // identity + dedup. Same key = same card.
  kind:       "proposal"         // a closed set, chosen by code
  status:     "needs_you"
  headline:   "Sarah Chen · Series A term sheet"  // plain text, no markdown
  source:     "gmail"
  occurred_at: "2026-08-21T14:14:00Z"
  importance: 0.82
  affordances: [draft_reply, snooze, dismiss]  // real capabilities, code-labelled
}

// the ONE thing the model writes. Markdown. muldro's voice.
body: "Sarah is asking for a decision by Friday. This is the third
       message in the thread and the first one carrying a deadline."

// external text — copied by code, never interpolated into `body`
quotes: [{
  text:  "Can you get back to me by Friday? The other LPs are waiting."
  who:   "Sarah Chen <sarah@…>"
  when:  "2026-08-21T14:14:00Z"
}]

Why key is the important field. It is what makes the three "New activity" cards impossible rather than merely unlikely. Today the unit is a poll cycle, so nothing can be the same as anything else. Give the frame a stable identity and a second message on the same thread updates the card instead of minting another.

The body is one field, and the card shows its first paragraph

A body can run long — a research finding, a briefing. It cannot all fit on a card, and the answer is not to cut it. The first paragraph is the lede: a complete, self-contained claim, written to a budget. The Glance renders that paragraph; the Full renders the whole document. The Glance is therefore literally a prefix of the Full — a semantic one, not a character count — so the two cannot disagree.

The budget belongs to the frame's kind, which means code sets it. The model is told how much room this particular object has and writes to it; it never decides how much room to take. An overrun is rejected and rewritten by the same typed-generation repair loop that already rejects bad tool arguments.

KindLede budgetFull bodyWhy
proposal~140 charsshort One thread, one reason it needs you. Longer means the model is padding.
finding~180 charsunbounded Research and synthesis are legitimately long.
briefing~90 charsunbounded Sits in a list of peers; the lede has to scan.
run~120 charsshort What it did. The steps carry the detail.

The second half of the rule is about shape, not length. Markdown can contain headings, lists, tables and code fences, and any of those rendered into a 320-pixel grid cell destroys the card however short it is. The Glance renders inline markdown only — emphasis and code spans. No blocks, and no links: a link in a body would reopen the injection question through a different door, so the model names a source and the frame links it.

Across connectors

The frame already exists

The obvious worry is that every source needs its own frame. It doesn't — every connector already normalizes to the same shape before perception ever sees it.

The frame is not a new thing to build per connector — it is a projection of NormalizedEvent, which already carries source, entity_type, entity_id, occurred_at, actor_entities, importance_score, urgency_score, correlation_id and idempotency_key — plus an index on (user_id, source, entity_id). The perception layer then throws it away and rebuilds a worse frame by concatenating rows into prose (perception_runner.py:279).

Two things fall out of the table. Four of five sources already key on a durable thing, not an occurrence — Fork 1's answer is implemented at ingestion and discarded downstream. GitHub is the lone outlier, keying on the notification id, so one PR collecting three review comments mints three identities; its raw_payload["url"] already holds the PR's own URL, so that is a one-line fix rather than an architecture problem.

And title is untrusted in all five, uniformly — so the rule that fixes it is one rule at one boundary, not five. Adding a sixth connector means filling in five fields, not building a card.

One more thing the table exposes: github sets actor={"type":"system","name":repo}, attributing the event to the repository and discarding the human who commented. That human is the counterparty the frame's headline needs.

Depth

Glance decides whether; Full decides what

A card cannot carry enough to decide on — but the fix is not a fuller card. Nineteen slots is what "put more on the card" already produced. The card's job is triage; the decision happens one level down.

The Glance must be uniform — you cannot rank things that don't look alike, and ranking is the entire feed. The Full must be faithful — an email thread rendered through a generic detail view stops being an email thread. Frame-and-body governs the Glance. The Full is a different contract, and that is not a contradiction: they answer different questions.

Four archetypes, not one per connector

The heterogeneity is smaller than it looks. A Gmail thread, a Slack thread and a GitHub PR discussion are all the same shape — ordered, attributed, timestamped messages. Grouping by the entity_type the connectors already emit gives four archetypes, derived from real content rather than chosen up front, which is exactly why the last catalog had seventeen.

Where the content comes from

Fetching live on open is never stale but fails exactly when you need it — your screenshot has gmail's circuit open, and clicking a card into "couldn't load" is worse than a thin card. Storing everything at perception time is instant but goes stale and quietly commits you to keeping full email bodies in Postgres.

Store the normalized archetype at perception time, refresh live on open. Instant paint, correct within a second, degrades to stored-only when the source is down. It isn't two code paths — it is one renderer over one archetype shape with two possible data sources, and the renderer cannot tell which it got. Storing the archetype rather than the raw provider blob does double duty: it bounds storage growth and it bounds sensitivity, because what persists is the messages muldro actually reasoned over, not every header Google returned.

The mechanism already exists. _fetch_thread_contexts (perception_runner.py:35) fetches full Gmail threads via get_gmail_thread_content today — then uses them to build a prompt and throws them away.

Chat and autonomous

One shape, two producers

The same object, the same renderer, on both paths. The asymmetry is not in the shape — it is that chat has an additional ephemeral channel the autonomous loop doesn't have, because chat is already framed by the thread you're reading.

The promotion decision is structural, not the model's opinion

"Did this turn produce something durable" is answered by looking at what the turn did — a run row was created, a write was staged as an approval, a finding was recorded — not by asking the model whether its answer was interesting. message_promotion.py already argues exactly this ("the gate is structural, not semantic — the agent does not self-evaluate usefulness"). It is right, and it is currently applied to a dead code path. The principle survives; its input changes from "which components did you emit" to "what did you actually create".

Decisions

The forks, and where each stands

Fork 1 Settled

What is the unit the founder sees?

One identity, two groupings layered on it. The key is (source, entity_type, entity_id) — what the connector already emits. A nullable group_key carries cross-source correlation. Goals are a view that groups by group_key, not a third scheme.

Identity must be deterministic or dedup isn't dedup: an inferred key lets two runs of one pipeline mint two keys for one thing, which is precisely the failure in the screenshot. The connector's key comes from the source system and cannot drift. Guardrail for the correlation layer: a merge must be reversible from the UI. A wrong rank the founder can route around; a wrong merge puts two contexts under one headline in muldro's voice, and they cannot undo it.

Fork 2 Superseded

Prose, or model-authored structure?

Folded into Fork 3. Prose — but the reason the trade felt painful was that killing model-authored structure seemed to kill affordances with it. Frame-and-body keeps them, because they were never the model's to author.

Worth stating plainly: render_surface has never rendered anything. The tool emits surface_id; the WebSocket handler guards on msg.surface?.id (use-muldro-ws.ts:127) and drops it. It returns {"status": "published"} either way, so the model believes it worked and writes only the short chat companion. Deleting it costs zero capability.

Fork 3 Settled

Who authors what?

Code owns the frame. The model writes one markdown body. External text is quoted by code and never enters either.

Collapses nineteen optional slots to a fixed frame plus one field, so two cards of a kind are the same shape by construction. Kills the double-render, the invented evidence, the model-minted capability, and the markdown link-injection hole in one move.

Fork 4 Settled

Does this apply to chat as well as the autonomous loop?

Yes — one shape, both paths. Chat additionally keeps an ephemeral prose channel, because a chat turn is already framed by the thread. The autonomous loop has no such channel.

The no-external-text rule applies equally, and this is the part that is easy to get wrong by assuming chat is safe. A chat turn puts GitHub and Gmail tool results into the lead's context; the lead can echo an issue title verbatim into its body. Same laundering, different door.

Fork 5 Settled

Should muldro remember what it told you?

Yes — a durable Finding that stores its own derivation. The claim, its sources, and how to recompute it: which tools ran, with which arguments, against which rows — plus as_of and stale_after. Fresh, it renders. Stale, it re-derives on view.

Storing the claim alone is a cache wearing a confidence badge — "you have four active repos" is true for an hour, and a stale finding is muldro confidently telling you something false. Storing only the question is never stale but costs a re-derivation on every view, and not everything is a query. Carrying the derivation on the row is the same invariant as everywhere else — a view is a pure function of a row — and it hands you the watch feature later for free: a finding with a short stale_after that the founder keeps opening is, definitionally, something to watch.

Fork 6 Settled

Is importance computed or scored?

Scored — but as a list-ranker over sanitized features, not an item-scorer over raw content. Structural signals become the features; the model does the commensuration over them; the engagement penalty is one more feature. One ranker, three contributions.

Some signals compare across sources — recency, addressed-to-you, reply-to-you, unresolved affordance. Importance itself does not. There is no shared scale on which a #general message, a review request and an investor email can be ordered, and a hand-tuned weight per source is just a guess at the commensuration a model does better. That is the case for scoring, and it holds.

Two things were conflated, and separating them is what makes scoring safe. What the ranker reads: today assess_relevance puts raw subjects and thread bodies into the prompt, so "THIS IS EXTREMELY URGENT" is an instruction to the scorer. Feed it muldro's derived facts instead — counterparty is a known entity, thread has N messages, you replied twice, a deadline was extracted to a typed date, it matches goal G — and the sender's prose never reaches it. An attacker can then lie about when, not inject an instruction. What it ranks: today it scores one signal alone, which is why it cannot commensurate and why 0.7 means nothing. Rank the whole open feed in one call and you get a real relative order, for one call per refresh instead of one per item.

Engagement is a feature, demotion only. Promotion by engagement is self-sealing: rank drives visibility, visibility drives engagement, so a low-ranked type is never seen, never engaged, and sinks forever — you could never discover you actually care about Notion edits. Demotion has no such loop, because you had to see a thing to dismiss it. Promotion needs deliberate exploration, and that spends founder attention on purpose — premature with no history at all.

Fork 7 Settled

How much does a card show, across five different sources?

Glance stays uniform and answers "does this need me?" Full is faithful to the source and answers "what do I do?" Four archetypes — Conversation, Change, Event, Document — cover all five connectors. Only layer 1 of the Full differs; muldro's reasoning, the cross-source join and the affordances are the same everywhere.

Uniformity and richness are not in conflict once the two levels have different jobs: you cannot rank things that don't look alike, and you cannot render an email thread faithfully through a generic view. Content comes from the stored archetype, refreshed live on open — instant, current, and still readable when the source's circuit is open. And the reason this beats a link to the source is layer 3: "Friday is the day before your board meeting" needs gmail and calendar and your goals joined, which only muldro holds.

Consequences

What stops existing

All of this exists to serve one premise — that the model should author structure. Once code owns the frame, none of it has a job.

Next

What lands first

Ordered by dependency, not by size. Each step removes its duplicate in the same commit — a second parallel path is how this got here.

1 · Frame from NormalizedEvent Identity is (source, entity_type, entity_id). Fix github's key to the PR, not the notification. Three duplicate cards become one that updates.
2 · Body as one markdown field Titles become plain text; external content moves to the quote band. Closes the injection hole. Deletes render_surface and the component catalog.
3 · Glance renderer One card shape, replacing nineteen optional slots. Every card of a kind now looks alike — which is what ranking needs.
