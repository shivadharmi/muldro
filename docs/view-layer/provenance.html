Where untrusted text goes

An inbound email is written by someone who is not your user and does not wish them well. This page traces every place that text can reach inside muldro, what it can do when it arrives, and why each door is shut by construction rather than by detection.

The vocabulary

Three authors, and only one of them is a stranger

Every value on screen has exactly one author. The whole design is the discipline of never letting the third kind wear the voice of the first.

code muldro's own logic over a database row. Headline, kind, status, counts, button labels.
model an LLM writing muldro's prose. Exactly one field — body — and nowhere else.
external an email subject, a message, a fetched page. The quotes band only, verbatim, attributed.

The rule that matters is enforceable rather than instructed. "Do not quote the email text in your summary" cannot be enforced, because the model holds the text and cannot prove it didn't use it. So the body slot never carries external provenance — because external values arrive on a different field that only code renders.

The set-piece

One subject line, traced

A real inbound subject, and the three slots it tries to reach.

inbound · gmail · From: a stranger
**URGENT** — [Verify your account](https://phish.example) — www.phish.example
frame.headline welded shut

Refused at the type boundary. The validator rejects every construct GFM would turn into emphasis, a heading, or a live link — including all three autolink forms — plus newlines and bidi overrides.

Length is bounded, not refused: a rejected headline is a card the founder never sees.

body no route in

The model writes this field, and the model has read the email — so this door cannot be closed by instruction. It is closed by giving external text somewhere else to go, where code renders it with a name attached.

The lede renders inline markdown only, and never a link.

quotes[] open, by design

Carried verbatim and never sanitized — neutralizing would misrepresent what the sender wrote, and a quote is evidence. Safety lives in the renderer, which never passes a quote to a markdown renderer.

An unattributed quote is dropped: with no name on it, it is indistinguishable from muldro's own voice.

The quieter vector

Wearing the voice, versus raising the rank

The headline attack makes untrusted text look like muldro. The second one never touches a word of copy — it just gets itself read first.

frame.importance was carried from an LLM score whose prompt interpolated Title: and Summary: — the raw subject and body. So THIS IS EXTREMELY URGENT in a subject line was not data to that model. It was an instruction.

was importance = _importance(event.importance_score)
# LLM output, over attacker-controlled text
now def frame_for_event(event, *, importance: float = 0.0)
# the caller's decision, like kind and status

The channel was removed, not defended. Nothing reads the field yet — which is precisely why it had to be closed now: the next feature to touch it would reasonably assume it was safe to sort on.

Why not just check it

A score cannot be verified. An order can.

The tempting fix is a second model that asks "is this genuinely important, or is it manipulating me?" But that is the question the first model was already asked — so the verifier is the scorer with extra steps.

a score: 0.0 – 1.0
  • ✗Unfalsifiable. 0.9 looks exactly as valid as 0.2. Importance is what you delegated — there is no outside fact to check it against.
  • ✗Unbounded. A fooled model puts the item first.
  • ✗Unlimited attempts. They send email until one lands. Your prompt does not iterate.
an order: a permutation of keys
  • ✓Totally checkable. Every input key exactly once. Nothing invented, nothing dropped — the output alphabet is fixed to the input.
  • ✓Bounded. Displacement is clamped: a maximally-fooled model moves an item a few places, not to the top.
  • ✓Fails whole. Anything that is not a valid permutation is discarded and the deterministic baseline stands. No partial trust.

And the ranker holds no prose at all — no headline, no summary, no snippet. It orders opaque keys. It cannot be prompted because there is nothing to prompt it with.

The part that scales

Provenance is a question you answer five times

A feature is not one decision. Each connector exposes different structure, so "where does a deadline come from" has five different answers — and two of them are "nowhere, yet".

Source Is summary verbatim? Structured deadline So a deadline comes from
calendar no — composed by muldro start_time the structured field. Never extract. The meeting's start is the deadline.
gmail yes — the message snippet none deterministic extraction
slack yes — the message text none deterministic extraction
github no — composed by muldro not captured nothing today. milestone.due_on exists in the API and the connector fetches neither.
notion no — composed by muldro not captured nothing today. Date properties exist; only last_edited_time is stored.

Calendar is the instructive row. Running a text parser over its composed "{title} from {start} to {end}" string would be strictly worse than reading the typed timestamp sitting beside it — and would open a parse surface where none existed. One general mechanism pointed at every source is how that mistake gets made.

The decision procedure

Ask this of every field, of every connector

“Is this a value the provider computed, a value a human wrote, or a value a model inferred?”

  • provider A typed value from the API. No parser to feed, nothing to inject. Always preferred where it exists.
  • human prose Deterministic extraction only — a parser, never a model. Attacker-influenced but bounded and checkable. Acceptable.
  • model inference Rejected. This is an assertion about attacker-controlled text wearing a typed name.

Only the first two may enter. A sixth connector means answering this five more times — once per feature — and the fail-closed default means forgetting to answer costs a signal rather than opening a hole.

There is one honest exception, and it generalizes: classify_by_rules reads mail headers — List-Unsubscribe, Precedence: bulk — which are attacker-writable, but only in the demoting direction. Adding List-Unsubscribe demotes the sender; omitting it merely declines a demotion they could not have claimed anyway. An input an attacker can only use against themselves is safe to read.
