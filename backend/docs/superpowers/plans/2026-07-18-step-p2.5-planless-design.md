# P2.5 — Planless Chat (drop the Planner from the chat single-lead path) — DESIGN

> Chat Permission Model, Phase 2.5. Spec: `docs/superpowers/specs/2026-07-13-chat-permission-model.md` §5.
> The design pass (brainstorm → written design) before any build, mirroring how P2 got its own
> design doc. On `rebuild/first-principles`. **STATUS: DESIGN — approved in brainstorm 2026-07-18;
> awaiting user spec review. Dormant behind a new `JARVIS_CHAT_PLANLESS` flag (default off) on top
> of the already-dormant `deep_single_lead` + `JARVIS_RUNTIME=deep` + `permission_mode`. Legacy /
> autonomous paths byte-neutral. ZERO migrations. BUILD DEFERRED to a later session.**

## 0. What settled the shape (grounded current-state, re-verified by name)

The one-line framing ("drop the Planner from chat") undercounts the reality. Four grounded facts
reshape the work (anchors as of the design pass; re-verify at build time):

1. **The chat Planner is LIVE on the single-lead path, not dead.** `_process_core`
   (`src/orchestrator/chat_processor.py`) ALWAYS builds a `PlanOutput` first — real Planner
   (`call_agent_stream("planner", …)`) or `intent_to_plan` fast synthesis — and only THEN runs
   `_run_single_lead(plan=plan, …)` (`chat_single_lead.py`), whose docstring says "The Planner
   already ran." So P2.5 is a **live reroute**, not a dead-code delete.
2. **`system.*` are NOT catalogued capabilities today.** `CAPABILITY_CATALOG`
   (`src/integrations/capabilities.py`) contains only `system.discovery`. The 4 *action* caps
   (`system.set_goal`, `system.set_instruction`, `system.schedule_reminder`, `system.add_to_brief`)
   exist ONLY as Planner step-strings consumed by `SystemCapabilityHandler`
   (`system_capability_handler.py`); `system.respond` / `system.acknowledge` are pure no-ops
   (`return {}`). "Promote to tools" = "catalog them for the first time + add tool wrappers."
3. **Scope source flips plan-union → connector allow-list, and that mapping is net-new.** Today the
   lead's `capability_scope` is `derive_lead_scope(steps, …)` (`lead_builder.py`) — the UNION of each
   plan step's authority. `get_user_connectors` (`integration_manager.py`) lists *installations*,
   not capabilities; nothing today maps "connected connector → its capability set."
4. **`user_steps` / `UserActionsReady` loses its producer** (fed by Planner `actor=="user"` steps).
5. **`write_todos` already runs but is inert** — in `DEEPAGENTS_BUILTIN_NAMES`, ungated, but its
   todos channel is surfaced nowhere today (P3 territory).

## 1. Goal & non-goals

**Goal.** On the deep chat single-lead path only, stop calling the Planner. The single lead already
self-plans via `write_todos`; today it *also* receives a `PlanOutput` it does not structurally need.
P2.5 removes that dependency so a chat turn is: validate → context → build lead from a
connector-derived scope → stream (self-plan + act via the agent loop, gated) → completion tail.

**Non-goals.** The autonomous path (Planner → GraphExecutor → TrustEngine, `perception_runner`) is
UNTOUCHED. The legacy chat path (flag off) is byte-identical. `write_todos` surfacing + `mode`
retirement + per-workspace `permission_mode` default are **P3**, not here.

## 2. Locked decisions (from the brainstorm, 2026-07-18)

- **D1 — one phased spec.** Full planless reroute designed as three sequential build-phases
  (P2.5a → P2.5b → P2.5c) in this one doc; each lands + is gated + reviewed independently.
- **D2 — drop `UserActionsReady` (YAGNI).** Planless chat emits no suggested-user-actions block;
  the lead can mention next steps in prose, and `write_todos` (P3-surfaced) becomes the real
  next-actions home. Autonomous/legacy path keeps `UserActionsReady`.
- **D3 — scope = internal-read floor ∪ authenticated-connector caps.** Precise, token-efficient,
  spec-faithful ("NOT whole-catalog"). Requires the net-new connector→capability mapping.
- **D4 — route EVERYTHING through the single lead.** The planless branch drops `classify_intent`,
  the fast-path, AND the Planner. No cheap conversational short-circuit; "hi" also goes through the
  lead. Uniform; also removes a Haiku call/turn.
- **D5 — `system.*` internal writes are ALWAYS-ALLOWED.** Exempt from `permission_gate` AND
  `write_lock` (they are the user's own memory: reversible, `self` blast-radius). Exemption mirrors
  the existing `DEEPAGENTS_BUILTIN_NAMES` pass-through.
- **D6 — dedicated `JARVIS_CHAT_PLANLESS` flag** (default `false`) gates ONLY the P2.5c reroute, so
  P2.5a/b land as inert additions and the Planner-drop flips independently for rollback (mirrors how
  `JARVIS_RUNTIME` staged 6A).

## 3. Design — the three phases

### P2.5a — `system.*` → internal tools (purely additive)

- **Catalog** the 4 action caps in `CAPABILITY_CATALOG` (`CapabilityFamily.SYSTEM`).
- **Add 4 `InternalToolDef`s** (the 3-place rule): `catalog.py` (`InternalToolDef`, `internal_mcp`,
  `_special`-free), `schemas.py` (Pydantic input model + `TOOL_INPUT_MODELS`), `intelligence_server.py`
  (MCP fn). Each tool impl calls the SAME service methods the handler already calls
  (`MemoryService.store_goal_memory` / `store_instruction_memory` / `store_briefing_memory`,
  one-shot `Schedule` row) — no business-logic duplication.
- **`SystemCapabilityHandler` is UNCHANGED** — the autonomous/legacy path (Planner → handler) keeps
  using it. `system.respond` / `system.acknowledge` stay no-ops in the handler; on the planless chat
  path they simply do not exist (the lead replies directly).
- **Agentic, not scripted:** the lead recognizes goal/instruction/reminder/brief intents and calls
  the tool (vs today's deterministic pre-lead handler run). A little guidance moves into the lead
  prompt / tool descriptions.
- **Gate exemption (D5):** `permission_gate` gains a `system.*` pass-through (after the
  `DEEPAGENTS_BUILTIN_NAMES` check) so these internal writes never interrupt and never take the
  write_lock, in any mode.
- **Audit:** the per-handler `PlanTask`+`InteractionLog` (keyed on `plan_id`) is not created on the
  tool path; the normal tool-call span audit in `agent_loop` (`TokenUsage trigger=tool:<name>`)
  covers it.
- **Ships first & independently** — additive (new tools + gate pass-through), touches neither the
  Planner nor scope; safe to land before anything reroutes.

### P2.5b — connector-scope source

New `resolve_connector_scope(user_id, workspace_id, db) -> frozenset[str]` (home: a small module
alongside `lead_builder.py`, or extend it):

- **`INTERNAL_READ_FLOOR`** (module constant): internal READ caps needing no external connector —
  `knowledge.*`, memory/world-model reads, `discover_capabilities`.
- **`SYSTEM_CAPS`** (module constant): the P2.5a `system.*` caps — always-available internal writes
  (D5), kept separate from the read floor since they are writes, not reads (the lead can always
  manage the user's own goals/memory).
- **Connector caps:** `get_user_connectors(user_id, workspace_id)` → keep only
  `status == active AND health_status healthy` → for each, map `provider → server_prefix` (the
  **net-new glue**) → `{tool.capability for tool in ToolRegistry where tool.server == prefix}`.
- **Scope = `INTERNAL_READ_FLOOR` ∪ `SYSTEM_CAPS` ∪ connector-caps.** Enforced by the existing
  `capability_scope` middleware
  (fail-closed); `get_tools_for_agent` offers only in-scope tools. Writes are in-scope but gated by
  `permission_gate` (except `system.*`, D5).
- **Dormant until P2.5c consumes it** — pure addition.

### P2.5c — drop the Planner + re-home (gated by `JARVIS_CHAT_PLANLESS`)

On the single-lead branch of `_process_core`, when the flag is on (and only under the dormant
`deep_single_lead` + `runtime==deep` + `permission_mode`):

- **Skip** `classify_intent`, the fast-path (`intent_to_plan`), the Planner call, `extract_plan`,
  `Plan` persistence, `PlanReady`, `resolve_plan_routing`, the deterministic pre-lead `system.*`
  run, and `UserActionsReady`.
- **Build the lead from `resolve_connector_scope`** (not the plan-union). `_run_single_lead` /
  `build_chat_lead` gain a planless entry that takes a `scope` instead of `steps` (the existing
  plan-driven entry stays for the flag-off path).
- **Re-home Planner byproducts:**

  | Byproduct | Planless re-home |
  |---|---|
  | `PlanOutput.steps` → lead scope | `resolve_connector_scope` (P2.5b) |
  | `system.*` steps | internal tools (P2.5a) — lead calls them |
  | `user_steps` / `UserActionsReady` | **dropped** (D2) |
  | `PlanReady` event, `Plan` DB record | **not produced** on planless chat (autonomous still does) |
  | `InteractionLog(plan=…)` | logged with `intent=None` (plan optional in signature) |
  | `plan.goal` / `reasoning` → `context_block` | omitted (lead has raw message + history) |
  | write-fence (fast-path diverts writes→Planner) | **retired** — permission_gate + write_lock + capability_scope are the write safety net |

- **The lead self-plans** via `write_todos` (native deepagents) + tool discovery + the agent loop —
  multi-step requests ("book a flight and email John") need no Planner DAG.

## 4. Activation / dormancy

`JARVIS_CHAT_PLANLESS` (settings flag, default `false`).
- **Off (default):** the single-lead branch calls the Planner exactly as today → byte-neutral.
- **On:** planless reroute, but ONLY when the single-lead path is already active
  (`deep_single_lead` + `runtime==deep` + `permission_mode`) — itself dormant in production.

So P2.5 ships **fully dormant, byte-neutral on every live path, ZERO migrations** (the `system.*`
tool defs seed via the existing catalog sync on restart; no schema changes — the caps live in
`tool_definitions` / `CAPABILITY_CATALOG`, both code+seed).

## 5. Safety invariants

- **Dropping the Planner removes ZERO write safety** — the Planner was never a write gate. Every
  *external* write on the planless lead is still gated by three independent mechanisms:
  `capability_scope` (fail-closed, only in-scope caps callable) → `permission_gate` (P2 confirm in
  ask/auto) → `write_lock` (P1/A3 fail-closed on Redis-down). The write-fence
  (fast-path diverting writes→Planner) was a fast-path artifact fully subsumed by `permission_gate`.
- **`system.*` internal writes are the sole, deliberate exemption** (D5) — internal, reversible,
  `self` blast-radius, the user's own memory.
- **Untouched:** autonomous path (Planner→GraphExecutor→TrustEngine, `perception_runner`) —
  byte-identical; legacy chat path (flag off) — byte-identical; `SystemCapabilityHandler` —
  unchanged.

## 6. Testing (per phase)

- **P2.5a:** `validate_registry` accepts the 4 new tools; each tool impl persists what the handler
  does (goal / instruction / reminder / briefing) via the shared service; `permission_gate`
  pass-through test (`system.*` never interrupts in ask/auto/bypass); existing
  `test_system_capability_handler.py` stays green (handler untouched).
- **P2.5b:** NEW tests for `resolve_connector_scope` = `INTERNAL_READ_FLOOR` ∪ `SYSTEM_CAPS` ∪
  authed-connector caps; unauthenticated / unhealthy connectors excluded; floor + system-caps always
  present; empty-connectors → floor + system-caps only; `provider→server_prefix` mapping covered.
  `derive_lead_scope` (plan-union) is UNCHANGED — it still feeds the flag-off + autonomous paths —
  so `test_lead_builder` stays green (additive, not a retarget).
- **P2.5c:** flag **on** + single-lead → assert Planner **not called**, no
  `PlanReady`/`Plan`-record/`UserActionsReady`, lead scope == `resolve_connector_scope`,
  reply + surface + learner (A1) still fire, a `system.*` tool is callable + ungated; flag **off** →
  byte-neutral (Planner still called). Retarget the chat-pipeline/orchestrator tests that assert
  "chat calls the Planner" — grounded candidate list (re-verify at build): `test_chat_pipeline*`,
  `test_orchestrator*`, `test_plan_creation`, `test_fast_path_no_write`, `test_cheap_mode`,
  `test_core_events`. Only the FLAG-ON assertions are new; flag-off keeps the existing assertions.

## 7. What P2.5 does NOT do (→ P3 / later)

- Surface `write_todos` (the todos channel) as a Claude-Code-style todo list → **P3**.
- Retire `mode` (ask/plan/execute) → `permission_mode` across API + frontend → **P3**.
- Per-workspace `permission_mode` default setting → **P3**.
- CLAUDE.md two-execution-paths rewrite → the eventual merge (**R1**).

## 8. Open questions / risks (resolve at build)

- **`provider → server_prefix` mapping** is the one genuinely net-new primitive. Confirm at build
  whether `IntegrationInstallation.provider` maps 1:1 to a `ToolRegistry` `server` value or needs a
  small lookup table; decide where it lives (integration layer vs tool registry).
- **`InteractionLog` / `log_interaction` signature** currently expects a `plan`; confirm it accepts
  `plan=None` cleanly (or add the optional) without breaking the autonomous callers.
- **Lead prompt guidance for `system.*`** — the lead must recognize "remember / set a goal / remind
  me" intents to call the new tools; validate the prompt/tool-descriptions carry enough signal
  (a behavior-parity check vs today's Planner-driven detection).
- **`build_chat_lead` planless entry** — add a scope-taking path without disturbing the existing
  plan-driven entry (flag-off must stay byte-identical).
